# Design Record — 2026-10 Audit Rulings

Non-normative. Rulings touched: the seven **ruled** items of the 2026-10
audit (item 4, `:=` layout; item 6, qualified names; item 10, cross-pattern
duplicates; item 14, float finiteness; item 15, anchored constructors;
item 16, `with` construction; item 17, selective import — Clauses 5–7, 9
and 10). Rejected alternatives, prior art, and rationale. The ten
**confirmed** items of the same audit record no decision: the normative
clause now states the implemented reading, and the clause is the whole
record of it.

## 1. `:=` never opens a block (Annex A.4 rule 6)

The block-layout license covers only the `:` and `=` tokens, so a multi-line
`:=` right-hand side can never receive a `NEWLINE INDENT ... DEDENT` wrapper:
the deeper lines parse as a spliced continued expression (Clause 6.2.4).

- **Rejected: a block-layout license for `:=`.** Letting a rebinding open a
  block would add a third block-introducing token and split the header table
  of Clause 6.2.3, whose members are declarations, from rebinding statements,
  whose right-hand side is an expression position. The single-rule reading —
  blocks open on `:` and `=` only, everything else continues under the
  licensed positions — keeps one mechanism for both flow shapes.
- **Prior art.** Python and Go assign without opening a block; a multi-line
  right-hand side is bracket or operator continuation. Eko follows them and
  cites the continuation clause instead of inventing an assignment-layout
  form.

**Ruling (2026-10-26).** The block-opening tokens are `:` and `=`; a line
that ends in `:=` opens no block, and a multi-line rebinding right-hand side
is a continued expression under Clause 6.2.4 (Annex A.4 rule 6).

## 2. A qualified name's head is the module path (Annex A.3.8)

Module stems are snake_case (Clauses 5.5.2, 7.2.1), so an all-Pascal
`QualifiedPascalName` could not spell `mod.Ctor`: the ruling changes the
production to `{ Identifier '.' } PascalName` — any-case head segments naming
the module path, one PascalCase last segment naming the type or constructor.

- **Rejected: PascalCase module stems.** Renaming modules to PascalCase (or
  admitting a Pascal alias for them) would create a second module-naming
  convention beside Clause 7.2.1's file-stem rule, and would leave every
  qualified function call — the far more frequent form — spelling its module
  in the other case. The grammar follows the module's actual case class.
- **Prior art.** OCaml's `Mod.Type` works because OCaml modules are
  capitalized; the mechanism Eko keeps is the head-names-the-module reading,
  not the casing. Java packages are lowercase under capitalized classes —
  the same shape Eko now states.

**Ruling (2026-10-26).** A `QualifiedPascalName` is a dotted name whose last
segment is PascalCase and whose head segments form a module path of any case
class; a module-qualified constructor application in value position is
spelled as a call, `geolib.Circle(r)` (Clause 6.5.2).

## 3. One arm's patterns bind together (Clauses 6.8.6, 7.7.1)

A multi-scrutinee `case` arm carries one pattern per scrutinee (Clause 6.7.2)
and constructs no tuple value, so the per-pattern duplicate rule of Clause
6.8.6 leaves the cross-pattern case formally unspecified. The ruling closes
it: the arm's patterns bind together as one pattern.

- **Rejected: OCaml-style last-wins.** OCaml accepts a repeated variable in
  one pattern with a warning; the later occurrence shadows the former
  (`(x, x) -> ...` binds `x` to the second component). Rejected here because
  a silent shadow inside one arm is a typo shaped like a program: every other
  Eko duplicate at one layer is `E-name-conflict`, and the arm is one layer.
- **Rejected: Erlang-style equality constraint.** Erlang reads a repeated
  variable in one head as a value equality test (`f(X, X)` matches only equal
  arguments). Rejected because it makes an accidental repeat into a guard —
  silent, unexhaustive-affecting, and invisible at the arm — and because Eko
  routes value comparison through `case` guards explicitly (Clause 6.7.3).
- **Prior art.** Rust rejects an identifier bound more than once in the same
  pattern; Swift does the same. Neither language has a multi-scrutinee arm,
  so the ruling generalizes their single-pattern rule across the arm.

**Ruling (2026-10-26).** The patterns of one arm of a multi-scrutinee `case`
bind together as one pattern: a name that occurs in two of the arm's
patterns is a duplicate and is `E-name-conflict` (Clauses 6.8.6, 7.4.6). The
compiler check is scheduled work.

## 4. A floating literal must be finite (Clause 5.7.2, Annex B)

`strtod` overflow on `1e999` yields `inf`; the audit left open whether a
`Float` literal needs a range check and, if so, with which code.

- **Rejected: a distinct `E-float-overflow` code.** The condition is the one
  Clause 5.7.1 already names — a literal outside the range of its target
  type — with `Float` as the target. A second code would slice one defect
  class by literal kind, and every consumer (tests, documentation, grepping
  users) would have to know both. `E-literal-overflow` is frozen and fits.
- **Rejected: allowing `inf` as a literal value.** Derived float operations
  follow the hardware and may produce `inf` (the library record's
  out-of-domain-is-a-value ruling); a literal is different — it is a
  placement, checked at compile time like every other literal. Admitting
  `inf` spelling would make the literal total and push a static defect to
  run time, and would give `1e999` and `Float.inf()`-style construction two
  truths. Operations may overflow; literals may not.

**Ruling (2026-10-26).** A floating literal denotes a finite `Float`; a
literal whose value is not finite after conversion is an error with code
`E-literal-overflow` (Clause 5.7.2, Annex B.3). The compiler check is
scheduled work.

## 5. Constructors are anchored, not layered (Clauses 7.2.5, 7.4.6, 7.6)

A constructor reference is selected by the type that anchors it, not by a
visibility layer. The question was whether same-named constructors from std
and from user declarations compete for one name slot or are resolved by the
expected type.

- **Rejected: the two-layer constructors reading.** A std constructor layer
  beneath user constructors — the implemented occlusion model, where user
  constructors are counted first and std is consulted only when none
  shares the name — makes a user `MyBool: type = True | False` occlude
  std's `True` everywhere. `x: Bool = True` then resolves `True` to MyBool
  and rejects a correct annotation. A name layer forces a winner exactly
  where the anchor should decide.
- **Rejected: the "default Bool" rule.** An unanchored ambiguous reference
  would silently prefer std's constructor. It is unnecessary — the
  unambiguous case already self-anchors — and harmful: it converts a
  missing annotation into a silent choice of the std type.
- **Prior art.** OCaml constructors are opened by opening their module, a
  name-layer model the ruling departs from. Rust enum variants are
  anchored by path or expected type: same-named variants of different enums
  coexist, and an ambiguous bare variant is an error.

**Ruling (2026-10-26).** Constructors never conflict by visibility;
constructors of different types may share a name. A reference is anchored
by the expected type in value position (Clause 7.5.2) or by the scrutinee
type in pattern position (Clause 7.7.1). An unanchored reference is legal
only when exactly one visible constructor of that name is non-generic
(Clause 7.6); otherwise it is an error, and an annotation anchors it.
Opened type names keep a shadowable fallback layer (Clause 7.2.5); free
names follow the ordinary import rules (Clauses 7.4.6, 9.1.2).

## 6. `with` is record construction from a base (Clauses 6.6.3, 9.8.6)

`r.with({...})` constructs a new record of the receiver's type: the literal
supplies the named fields, and every field it does not name takes the
receiver's value. The question was how far a partial literal may descend
into the values it completes.

- **Rejected: single-layer `with`.** Restricting the partial literal to the
  receiver's top-level fields would forbid a record-typed field from taking
  a partial literal of its own. Construction from a base naturally
  continues through a record field: the nested value is a record built from
  the receiver's field, the nested `..base`.
- **Rejected: `with` as a function or method.** Its second parameter type,
  `(t, partial fields) -> t`, is not expressible in the type syntax, and a
  partial literal is legal only in that argument position. Framing it as an
  ordinary callable would require both a type the language cannot spell and
  a literal form legal nowhere else.
- **Prior art.** Rust's struct expression `Wrapper { name, a }` constructs
  by naming fields, and its base completion `Wrapper { x: 1, ..p }` fills
  the rest from `p`. A nested record field is another struct expression.

**Ruling (2026-10-26).** `with` is a construction primitive wearing
member-call syntax, not a function. The partial literal descends through
record field values only; it does not descend into list, dictionary, or
tuple elements, where an element literal is a complete value and a partial
literal is an error. The original value is unchanged; there is no mutation
(Clauses 6.6.3, 9.8.6).

## 7. Selective import; std is an ordinary module (Clauses 6.1, 7.2.3, 7.2.5, 9.1.1, 9.1.2, 9.2.3, 9.8.1, 9.14.3)

std is an ordinary file module. The compiler's only act is the injected
import line; no name rewriting occurs, imports open types, and functions
stay module-qualified (Clause 7.2.3). Bare `assert()` needs a
name-entering mechanism for imported free functions; the ruling resolves
the contradiction with one general feature and one decomposition.

- **Rejected: O1, open-all.** Bare `import std` would open every free
  function of std. Every new std function would then enter every file
  silently, and every file top-level binding of a matching name would
  collide; the opened vocabulary would move with a library update.
- **Rejected: O3, module-side designation.** The imported module would
  declare which of its names it opens. That puts the importer's namespace
  decision in the imported file: two importers could not choose different
  lists, and a library edit would change every importer's scope.
- **Rejected: O6, test-scoped vocabulary.** The assert family would be
  opened only in test compilation. It is ordinary std source usable outside
  tests, and a scope rule keyed on compilation mode makes the same source
  mean different things.
- **Rejected: C, capability-qualified assertions.** `Determinism.assert_eq`
  would tie an ordinary pure std function to a capability it does not use.
- **Rejected: A, the `Bool.assert` split.** Assertions would become methods
  of `Bool` or of a helper type. `assert_eq` and `assert_ne` are generic
  over two same-typed arguments, not methods of one receiver; the split
  multiplies names without removing the opening question.
- **Rejected: panic as std source over the abort primitive.** Clause 9.1.1
  promises that every other standard-library service is ordinary Eko
  source, and abort lies beneath source; a compiler-provided body in std
  would be the one exception the doctrine forbids.
- **Rejected: panic by a special name rule.** That is the six-name list
  again — a name-entering mechanism for one compiler-generated service.
- **Prior art.** Gleam's `import m.{f}` is the exact selective-import prior
  art. Rust prelude versioning treats the injected set as a language
  constant: it moves only by language revision.

**Ruling (2026-10-26).** The injected line
`import std.{assert, assert_eq, assert_ne}` is ordinary syntax; all three
names are ordinary std source. `show` and `inspect` are compiler-generated
services attached to every type namespace, and `panic` is the
compiler-generated service of String's namespace; each free-call form is
the identity of Clause 6.5.2 — `show(t)` is `t.show()`, `panic(m)` is
`m.panic()`. An opened free name collides at the declaration point: an
opened name beside a file top-level binding, and two imports opening the
same name, are `E-name-conflict`; locals shadow legally (Clauses 7.2.3,
7.4.6).

A new std free function is immediately usable qualified (`std.newf(x)`) and
bare for any user who writes `import std.{newf}`; the injected list does
not move, and moving it is a language revision. New std types open
automatically and are shadowable under item 15's fallback exception —
non-breaking. New namespace members ride their types — non-breaking, but
with a known capture hazard: a new std namespace member can silently win
station 2 over a user's same-named station-3 function (Clause 7.4.3). The
hazard is recorded and deliberately not fixed.

## 8. Corpus rulings (2026-10-27)

The example corpus (a todo application and a Lua interpreter, ~2,300
lines) was run through the finished front half; its residual diagnostics
were ruled on one by one by the spec owner.

- **G1, arm bodies open blocks (amendment).** A `case` arm line ending in
  `->` opens the arm body block; the last member is the arm's value
  (Clause 6.2.3, Annex A.4 rule 6, A.3 Arm). Rejected: inline suites only,
  forcing multi-statement arms through immediately-invoked lambdas or
  `if`/`else` chains — the block mechanism already exists for `:` and `=`,
  and the corpus uses the shape pervasively. The opener is token-based, as every A.4 rule
  is: a depth-zero line ending in `->` opens a block even where a type
  annotation might have been meant — such a break was never licensed by
  Clause 6.2.4, and the grammar now rejects it at parse instead of the
  layout silently splicing it.
- **G2, type aliases stay out (rejection).** `Name: type = <type
  expression>` remains illegal (Clause 6.9.5, the 6.10 table). Rejected:
  transparent aliases — they erode nominal identity (is `Env` `[]Scope`?
  every judgment must say), the cheap expansion is available by hand.
  Prior art: Go ships without aliases by choice; Haskell's `type` versus
  `newtype` split is the confusion avoided.
- **G3, composite generic arguments stay parenthesized (re-affirmation of
  item 7).** `Result ([]String) String`, never `Result []String String`.
  The bare form is lexically indistinguishable from a juxtaposed
  application at the same position; item 7 of this audit confirmed the
  parentheses and the corpus is corrected instead.
- **G4, calls keep their parentheses (rejection).** Juxtaposition stays
  the constructor application (Clause 6.5.2); `Int.to_float i` is an
  error. Rejected: generalized juxtaposition — `f a b` then must choose
  between two arguments and curried application, a whole-chapter grammar
  change bought at permanent ambiguity cost.
- **G5, the empty interpolation slot stays an error (re-affirmation).**
  `"{}"` is `E-empty-slot` (Clause 5.9.3); a literal brace is `"\{"`.
  The corpus line is corrected.
- **G6, an example defect (correction).** The interpreter's `_index_get`
  signature disagreed with its caller; the example is corrected to the
  `Result ([State, Value]) String` shape. No spec change.
- **G7, `==` stays value-layer (re-affirmation).** ADTs compare through
  the derived `eq` (Clauses 7.8.3, 9.8.4); the example lines become
  `.eq` calls. Rejected: desugaring `==` to derived equality — it would
  blur the E-no-eq boundary the world rules lean on and change the
  diagnostic surface N13 tests.
- **G8, operand lambdas are parenthesized (corrigendum, 2026-10-27).**
  `if (a) || (b): 1 else: 2` misparsed: the operand `(b)` read as the
  parameter group of a lambda that swallowed the header's colon. Ruled:
  in operand position — a unary or binary operand, or the argument of a
  constructor application by juxtaposition — `( parameters ) :` is a
  grouping followed by the enclosing header's colon; the lambda form
  there must be parenthesized (Clause 6.4.1). Rejected: reading the
  lambda maximally in every position — it makes every parenthesized
  operand before a header colon unspellable. Prior art: Swift requires
  parentheses around trailing closures in ambiguous positions; the
  house style already demands parentheses for composite generic
  arguments (item 7, G3).
